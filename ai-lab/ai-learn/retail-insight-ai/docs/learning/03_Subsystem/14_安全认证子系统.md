# 一、子系统定位

安全认证子系统负责保护整个系统。

主要职责：

-   用户身份认证（Authentication）
-   用户权限控制（Authorization）
-   API 安全访问
-   审计日志（Audit Log）
-   企业安全治理

一句话：

> **Authentication 负责确认"你是谁"，Authorization
> 负责确认"你能做什么"。**

# 四、Authentication（身份认证）

Authentication 用于验证用户身份。

常见方式：

-   Username / Password
-   API Key
-   OAuth2
-   JWT
-   SSO（企业单点登录）

流程：

``` text
User
   │
Login
   │
Verify Identity
   │
Token
```

------------------------------------------------------------------------

# 五、Authorization（权限控制）

认证成功后，还要判断是否有权限。

例如：

``` text
Admin
 ├── Upload Document
 ├── Approve
 └── Manage Users

Analyst
 ├── Create Task
 └── View Report

Viewer
 └── Read Only
```

------------------------------------------------------------------------

# 六、RBAC（Role-Based Access Control）

企业通常采用角色权限模型：

``` text
User
   │
Role
   │
Permission
   │
API
```

优势：

-   权限集中管理
-   易于扩展
-   符合企业治理

------------------------------------------------------------------------

# 七、Audit Log

关键操作需要记录：

``` text
User Login
Create Task
Approve
Delete Document
Change Role
```

Audit Log 应保存：

-   用户
-   时间
-   操作
-   结果
-   IP（如需要）

便于审计与问题追踪。

------------------------------------------------------------------------

# 八、与 AI Workflow 的关系

``` text
User
   │
Authentication
   │
Authorization
   │
Create Task
   │
AI Workflow
```

Workflow 不负责认证，而是依赖安全子系统提供的身份与权限。

------------------------------------------------------------------------

# 九、与 Approval 的关系

审批通常要求更高权限：

``` text
Approval
   │
Check Permission
   │
Approve / Reject
```

RBAC 可以限制只有审批角色才能执行批准操作。

------------------------------------------------------------------------

# 十、企业为什么这样设计（Why）

安全能力独立成子系统：

``` text
Security
    │
Authentication
Authorization
Audit
    │
Business Modules
```

这样：

-   所有模块统一使用
-   避免重复实现
-   更符合企业规范

# 十四、面试回答

项目将认证、授权和审计能力独立为安全认证子系统。Authentication
负责确认用户身份，Authorization 基于 RBAC 控制接口访问权限，Audit Log
记录关键操作，实现企业级安全治理。这样业务模块无需重复实现安全逻辑，便于统一维护与扩展。
