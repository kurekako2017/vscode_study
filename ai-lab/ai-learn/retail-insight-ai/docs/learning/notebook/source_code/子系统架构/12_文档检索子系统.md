# 一、子系统定位

文档检索子系统负责管理企业知识库。

主要职责：

- 文档上传
- 文档保存
- 文档查询
- 文档删除
- 为 AI Workflow 提供知识来源

一句话：

> 文档检索子系统负责"管理知识"，AI Workflow 负责"使用知识"。

---

# 二、源码位置

```text
backend/
└── app/
    ├── api/
    │   └── documents.py
    ├── services/
    ├── repositories/
    └── workflow/
```

`documents.py` 是 HTTP 入口，Repository 负责数据存储。

# 四、文档生命周期

```text
上传
  │
解析
  │
保存
  │
建立索引
  │
查询
  │
提供给 AI
```

企业版通常还会增加权限控制、版本管理和审核流程。

---

# 五、Documents API

主要负责：

- 接收上传请求
- 参数校验
- 调用 Service
- 返回处理结果

它不直接进行检索或 AI 分析。

---

# 六、Repository

Repository 保存：

- 文档元数据
- 文档内容
- 文档状态

未来可以替换：

```text
InMemory
    │
SQLite
    │
PostgreSQL
```

无需修改业务层。

---

# 七、Internal RAG 流程

概念流程：

```text
Question
    │
Retriever
    │
Relevant Documents
    │
LLM
    │
Answer
```

当前项目提供了文档检索能力，为后续 RAG 扩展预留了接口。

---

# 八、未来企业版扩展

# 十一、企业为什么这样设计

拆分：

```text
Documents
      │
Repository
      │
Retriever
      │
Workflow
```

优点：

- 知识管理独立
- Workflow 可复用
- 检索算法可替换
- 易于扩展 RAG

# 十四、面试回答

项目将文档管理与 AI Workflow 解耦。Documents API
负责知识管理，Repository 负责存储，Workflow 在 Research
阶段调用文档检索能力，为 LLM 提供上下文。未来可平滑扩展到
LangChain、Embedding、pgvector 和 Hybrid RAG。
