## 第一章 项目概述

**Enterprise Retail Intelligence Platform（ERIP）V1.0** 是面向日本小売企业的经营智能平台。

目标客户角色：经营企画、商品部、库存管理、会员运营、门店管理、manager 审批者。

核心目标：把“会前找资料 → 做分析 → 写董事会报告 → 上长审批 → 留审计与成本台账”变成可重复、可权限控制、可追踪的企业系统。

**统一业务主链：**

```text
登录/JWT/RBAC
→ 文書管理
→ Upload
→ Import
→ Chunk
→ RAG検索/Citation
→ 显式 AI分析（low_cost）
→ 生成取締役会报告（high_quality）
→ Report/ReportVersion
→ 提交 Approval
→ manager审批
→ Persistent Audit
→ LLM Usage Ledger
```

**技术定位（现状，不是规划）：**

```text
React（正式 Frontend + ProtectedRoute + 权限导航）
→ FastAPI
→ Service 层
→ PostgreSQL / pgvector（正式 Repository）
→ LLM Gateway（默认 stub）
→ Persistent Audit / Usage Ledger
```

【为什么这样设计】

日本零售经营会议不是一次性聊天。证据、分析、报告版本、人审、审计、成本必须同链。ERIP 以企业交付为目标，而不是 Demo 展示。

【调用顺序】

```text
Browser
↓
React 正式页面
↓
JWT + RBAC
↓
Documents / RAG / AI Analysis / Executive Report / Approval
↓
PostgreSQL + Audit + Ledger
↓
（可选）LLM Provider via Gateway
```

【TL Review】

- 是否先讲业务主链再讲技术名词。
- 是否把 InMemory 误说成正式运行模式。
- 是否把默认 stub 说成已验证真实模型。

## 第二章 行业背景

日本零售经营管理重视：

- 月次经营会议
- 多店舗差异
- POS / 库存 / 商品 / 会员 / 促销
- 社内报告、FAQ、会议资料
- 上长承認与事后审计

数据常见形态：CSV、Excel、Markdown 社内文档、API 抽取结果。系统必须能把“文档证据”变成可检索、可引用、可审批的经营材料。

【为什么这样设计】

如果只做 KPI 数字看板，无法覆盖“依据哪份资料得出结论”。如果只做聊天式 LLM，无法覆盖权限、版管理、审批与成本。ERIP 把两者放进同一企业主链。

## 第六章 核心模块设计

### 6.1 Authentication / JWT

- `POST /api/v1/auth/login` 签发 Access Token  
- 本地确定性账号：admin / manager / employee  
- `GET /api/v1/users/me` 返回身份；权限由 Registry 推导  
- Frontend：`sessionStorage` 键 `erip.access_token`  

### 6.2 Documents

- Upload session + 幂等键  
- documents 保存元数据与 content  
- Import 流水  
- Chunk（可 replace）+ 可选 embedding  
- Archive  

### 6.3 Retrieval / Internal RAG

- document-retrieval：检索候选  
- internal-rag：grounded answer + citations  
- 默认不经 Gateway 调真实 Provider  

### 6.4 AI Analysis

- 仅显式 `POST /api/v1/ai-analysis`  
- 需要 confirmed、Evidence、Idempotency-Key  
- low_cost 政策 + 额度预占 + Ledger 结算  

### 6.5 Executive Report

- high_quality  
- 生成 Report / ReportVersion  
- **不**自动进入 approved  

### 6.6 Approval

- submit / list / detail / approve / reject / revise / resubmit  
- ownership + permission 组合  
- History append-only  

### 6.7 Persistent Audit

- 成功/失败都可记  
- 业务 savepoint 与审计提交分离策略  
- 不含 Secret/全文  

### 6.8 AI Runtime

- 表 `ai_runtime_settings`  
- `GET/PATCH /api/v1/admin/ai-runtime`  
- Kill Switch → stub  
- InMemory → 503  

### 6.9 Frontend 页面模块

| 页面 | 文件 | 关键能力 |
|---|---|---|
| Login | LoginPage.tsx | 登录 |
| 学习总览 | DashboardPage.tsx | 入口 |
| 文書管理 | DocumentsPage.tsx | 上传/导入/切片/跳转 RAG |
| RAG/AI分析 | RagPage.tsx | 检索/RAG/AI/报告/提交审批 |

## 第七章 技术选型与设计决策

### ADR-001 正式 Repository 选择 PostgreSQL

- 原因：事务、行锁、append-only 表、pgvector、Alembic、企业验收一致性  
- 结果：页面与 E2E 以 PostgreSQL 为准  
- InMemory 仅测试  

### ADR-002 业务禁止直连 LLM SDK

- 原因：成本、超时、审计、模型切换必须收敛  
- 结果：`LLMGatewayService` 唯一外呼  

### ADR-003 普通 RAG 与显式 AI 分离

- 原因：会前检索应低成本；分析才进入可能收费路径  
- 结果：Internal RAG 默认可零真实 LLM  

### ADR-004 双路由 low_cost / high_quality

- 原因：分析高频、董事会报告高要求  
- 结果：Operation Policy 服务端固定，客户端不可改价  

### ADR-005 报告与审批解耦

- 原因：生成 ≠ 批准  
- 结果：ReportVersion 后需人工 submit-approval  

### ADR-006 JWT 不承载权限列表

- 原因：权限策略变更不应等 Token 过期  
- 结果：role + Registry  

### ADR-007 金额使用 Decimal

- 原因：float 不适合账本  
- 结果：Ledger / quota 全 Decimal  

### ADR-008 AI Runtime 持久化到 PostgreSQL

- 原因：进程内配置重启丢失，多实例不一致  
- 结果：`ai_runtime_settings` + 乐观锁 version  

### ADR-009 本地开发与 Compose 双路径

- 原因：日常开发不必强依赖 Docker Desktop  
- 结果：5173 宿主 PG；8080 Compose；数据不共享  

### ADR-010 默认 stub 验收

- 原因：零费用证明业务主链  
- 结果：未跑真实付费 smoke 不宣称模型效果

## 第九章 业务流程

### 9.1 标准会前流程

```text
1. admin/manager/employee 登录
2. 文書管理上传 Scenario 或业务文档
3. Import → Chunk，确认 searchable
4. 「使用此文档检索」进入 RAG/AI分析
5. Retrieval / Internal RAG 确认 Citation
6. 需要时：二次确认后执行 AI分析（low_cost）
7. 生成取締役会报告（high_quality）
8. 「提交审批」进入承認管理
9. manager 审批
10. 审计与（AI 路径）Ledger 可追溯
```

### 9.2 审批分支

```text
pending_approval
├── approve → approved
├── reject → rejected → revise → revised → resubmit → pending_approval
└── 并发/重复 pending → 409
```

### 9.3 权限分支

```text
employee：可 submit，不可 approve（403）
manager：可 review / approve / reject
admin：含 security.manage（AI管理）
```

- 成功响应包在统一 `ApiResponse`  
- 权限失败 403，未认证 401，冲突 409，Runtime 不可用 503  
- 写操作尽量挂 Persistent Audit

## 第二十四章 生产事故与调查顺序

### 通用调查顺序

```text
1. request_id
2. HTTP status / error_code
3. Persistent Audit
4. 业务状态（document/approval/report）
5. llm_usage_ledger / provider_attempts
6. Backend 结构化日志
7. PostgreSQL 行
8. Frontend 会话与权限
```

### 事故型问题（面试可用）

1. **AI 分析 429**：额度桶与 Ledger reserved  
2. **approve 403**：角色与 permission  
3. **submit 409**：已有 pending  
4. **Runtime 409**：expected_version 冲突  
5. **503 AI Runtime**：InMemory 或不支持后端  
6. **RAG 无结果**：未 Import/Chunk 或过滤条件  
7. **报告成功但无审批**：未 submit（设计如此）  
8. **Compose 不健康**：postgres → alembic → backend → frontend 顺序  
9. **5173 不能业务测**：只起了 Vite  
10. **费用异常**：确认是否误开真实 mode
