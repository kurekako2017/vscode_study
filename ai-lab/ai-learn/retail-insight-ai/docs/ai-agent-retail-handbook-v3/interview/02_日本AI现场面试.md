## 第四章 技术设计问答

### なぜ業務から LLM SDK を直接呼ばないのですか。

```text
課金・タイムアウト・プロンプト・証跡・権限を一箇所で統治するためです。
LLMGatewayService が唯一の外向き入口です。通常 RAG は既定で Gateway を通さず、
明示 AI 分析と取締役会報告だけが Gateway を通ります。
```

### なぜ low_cost と high_quality を分けますか。

```text
分析は頻度が高くコストを抑え、取締役会報告は品質要件が高いからです。
Operation Policy で route_tier、上限、Evidence 要件をサーバ側で固定し、
クライアントから金額やモデルを上書きさせません。
```

### 通常 RAG は LLM を呼びますか。

```text
既定では呼びません。Document Retrieval と deterministic / extractive 合成で
Citation 付き回答を返します。実費用ゼロで根拠確認ができます。
```

### なぜ FastAPI ですか。

```text
HTTP 境界、依存注入、OpenAPI、非同期 I/O と型付き schema が企業 API に向いています。
Route は薄く、Service に業務を寄せる構成にしています。
```

### KPI任务分析 は何ですか。

```text
補助ラインです。/analysis から Task API を使い KPI / Research 系タスクを実行します。
企業主鎖の中心は文書→RAG→AI→取締役会報告→承認です。KPI は会議資料の補完位置付けです。
```

## 第五章 安全与审批问答

### JWT はどこに保存しますか。

```text
sessionStorage の erip.access_token のみです。localStorage には置きません。
権限一覧は Token に埋め込まず、role から Registry で導出します。
```

### 401 と 403 の扱いは。

```text
401 は未認証：セッションを破棄して再ログイン。
403 は権限不足：セッションは維持し、拒否を表示します。
```

### fail-closed とは。

```text
未知 role や不明 permission は許可しません。デフォルト許可は禁止です。
```

### employee が approve すると。

```text
Backend が 403 を返します。employee は approval.submit までで、
approve / reject は approval.admin（manager / admin）です。
拒否は Persistent Audit に残ります。
```

### ReportVersion はなぜ必要ですか。

```text
承認対象を不変スナップショットに固定するためです。
差し戻し後の改訂は新しい version を作り、旧本文を上書きしません。
```

### Approval の HTTP を教えてください。

```text
submit-approval は 201 pending_approval。
approve 成功は 200 approved。
同一 task の二重 pending は 409。
ownership 外の revise は 403。
```

## 第六章 LLM 治理问答

### Evidence Gate はなぜ必要ですか。

```text
根拠なし分析と幻覚課金を防ぐためです。証拠不足なら分析を拒否します。
```

### Idempotency-Key は。

```text
同一分析の二重送信による二重課金・二重予約を防ぎます。衝突は 409 系で扱います。
```

### Decimal を使う理由。

```text
金額に float を使うと丸め誤差が出ます。Ledger は Decimal で token / cost を確定します。
```

### Fallback の順序は。

```text
OpenRouter → NVIDIA → Gemini → Local Qwen の固定直列です。
熔断が open の Provider はスキップします。状態は PostgreSQL に共有します。
```

### AI Runtime 設定はどこにありますか。

```text
PostgreSQL の ai_runtime_settings です。mode / kill_switch / version を永続化し、
Secret は保存しません。Admin は GET/PATCH /api/v1/admin/ai-runtime。
InMemory では 503 fail-closed です。
```

### デフォルトは有料モデルですか。

```text
いいえ。既定は stub です。有料 smoke を実行していない場合、
実モデル品質を検証済みとは言いません。
```

## 第七章 数据与部署问答

### なぜ PostgreSQL が正式 Repository ですか。

```text
ページ業務、企業受入、Approval、Audit、Ledger、ReportVersion、AI Runtime を
永続化し、トランザクションと行ロックで整合を取る必要があるからです。
```

### InMemory は何のためですか。

```text
自動化ユニットテストの高速アダプタと障害隔離用です。
正式画面・企業受入・本番 Repository ではありません。
```

### Alembic head は。

```text
20260717_08_ai_runtime です。Compose 起動時に upgrade head します。
```

### 5173 と 8080 の違いは。

```text
5173 はローカル完全開発（宿主 PostgreSQL + Backend + Vite）。
8080 は Compose（PostgreSQL + Backend + Nginx Frontend）。
データソースは別です。5173 はフル起動後に実業務テスト可能、Vite 単独では不可。
```

### Compose で down -v してよいですか。

```text
通常は禁止です。erip_postgres_data を消すと業務データが失われます。
明示指示がある場合のみです。
```

### テスト数は。

```text
PostgreSQL Backend 297 tests / 6 skipped。
InMemory Backend 286 tests / 62 skipped。
Frontend 116/116。production build 通過。
```

## 第八章 深掘り 30 题

### 1. この案件で一番工夫した点は何ですか。

```text
「AI を呼ぶこと」ではなく、根拠・権限・版管理・承認・監査・コスト台帳を
業務主鎖に組み込んだ点です。通常 RAG は低コスト、明示 AI だけ課金統治します。
```

### 2. なぜ全部 Agent にしなかったのですか。

```text
文書 Import、Chunk、Approval 状態遷移、Ledger 予約など決定的処理は
固定 Service / 状態機の方が検証可能です。Agent は不確実な調査に限定します。
```

### 3. なぜ Task API もあるのですか。

```text
KPI任务分析の非同期実行と進捗通知のためです。企業主鎖の中心は文書と承認ですが、
会議資料の KPI 補完として Task API を維持しています。
```

### 4. SSE はどこで使いますか。

```text
主に Task 進捗通知です。文書主鎖の承認・分析は request/response + 状態取得が中心です。
```

### 5. ProtectedRoute の役割は。

```text
未ログインを遮断し、必要なら元 URL を覚えてログイン後に戻します。
権限の最終判断は Backend です。
```

### 6. フロントの権限とバックエンドの権限の違いは。

```text
フロントはナビとボタンの UX。バックエンドの require_permission が権威です。
フロントだけ許可しても API は 403 になります。
```

### 7. owner とは何ですか。

```text
承認を submit した本人です。detail は owner または review 権限、
revise は owner または approval.admin です。
```

### 8. History と Audit の違いは。

```text
History（approval_events）は業務軌跡。Audit（audit_logs）はセキュリティ/コンプライアンス事実。
本文全文はどちらにもコピーしません。
```

### 9. request_id は何のためですか。

```text
1 リクエストを API・Service・Audit で横断追跡するためです。
障害調査の第一キーです。
```

### 10. 二重 submit をどう防ぎますか。

```text
pending の partial unique と行ロックで、同一 task の二重 pending を 409 にします。
```

### 11. AI 分析の必須条件は。

```text
JWT、analysis.execute、confirmed、Evidence、Idempotency-Key、枠内予約です。
```

### 12. 取締役会報告後に自動承認しますか。

```text
しません。生成後は ReportVersion を残し、人が submit-approval します。
```

### 13. Fallback 失敗時は。

```text
チェーンが尽きたら失敗として Ledger / Audit に残し、業務を成功扱いしません。
```

### 14. Kill Switch は。

```text
ai_runtime_settings.kill_switch が有効なら effective_mode を stub に強制します。
再起動後も PostgreSQL から復元します。
```

### 15. Secret はどこにありますか。

```text
Backend プロセスの環境変数のみ。DB・Frontend・Audit 詳細に置きません。
```

### 16. pgvector の位置は。

```text
document_chunks に embedding を載せられる PostgreSQL 拡張です。
企業検索の永続層として PostgreSQL に統合しています。
```

### 17. seed_scenario01 は何をしますか。

```text
ログイン後、Scenario01 文書 01-06 を Upload/Import/Chunk する PostgreSQL 専用シードです。
Retrieval/AI/承認/有料 LLM は実行しません。冪等です。
```

### 18. Lifecycle Live Status は本番監視ですか。

```text
いいえ。Frontend の学習/診断用トレースで Backend に送りません。
本番 APM や SIEM の代替ではありません。
```

### 19. Redis は導入済みですか。

```text
本倉のデフォルト実行スタックには入れていません。将来のキャッシュ/キュー候補として説明します。
```

### 20. RabbitMQ は。

```text
同様に既定スタック外です。長時間ジョブの本格キュー化は今後の拡張です。
```

### 21. SSO は。

```text
現在はローカル JWT ログインです。Identity Provider 置換可能な seam を残しています。
```

### 22. 多店舗 ACL はどこまでですか。

```text
現在は role ベース RBAC が中心です。店舗/部署粒度の細かい ACL は今後強化点です。
```

### 23. 性能試験は。

```text
機能・結合・E2E（stub）と Frontend 116 を優先しています。
大規模 load test 数値は提示できる既定成果としては持っていません。
```

### 24. OpenTelemetry は。

```text
request_id 等の構造化ログを基盤にしています。フル OTel パイプラインは今後です。
```

### 25. なぜ Docker Compose が必要ですか。

```text
PostgreSQL + Backend + Frontend を同一構成で再現し、Alembic と healthcheck 付きで
企業受入・デモを安定させるためです。日常開発は宿主 PostgreSQL でも可能です。
```

### 26. 障害調査の順番は。

```text
request_id → Audit / 業務状態 → Ledger / Provider attempts → Backend ログ → DB 行 → Frontend 表示。
```

### 27. KPI の数字がおかしい時は。

```text
入力データ、固定計算ロジック、task イベント、report 版を順に確認します。
LLM の幻覚と KPI 計算を混ぜません。
```

### 28. CSV 形式が変わったら。

```text
schema 検証で fail-fast し、部分成功を曖昧にしない。Import 状態と Audit を残します。
```

### 29. チーム分担なら。

```text
Frontend / API / RAG / LLM 治理 / Approval・DB / 品質保証。契約（OpenAPI・権限・状態機）を先に固定します。
```

### 30. 次に強化するなら。

```text
有料 smoke の選択的自動化、Billing UI、多テナント予算、SIEM 連携、SSO です。
既にできた JWT/RBAC や Approval を「未完成」とは言いません。
```

```text
実装範囲と未実装を分けて説明します。
```

### 3. 本番障害対応の経験はありますか？

```text
商用障害チケット件数を盛ることはしません。
代わりに、timeout・403・409・Ledger 失敗・Compose 障害時の調査手順を説明できます。
```

### 4. 本当に LLM を理解していますか？

```text
本プロジェクトでは Gateway、Evidence Gate、双ルート、Fallback、Ledger、Runtime を実装しています。
既定は stub で、有料品質検証は別途 smoke が必要だと説明します。
```

### 5. RAG は実際どこですか？

```text
文書 Chunk 後の document-retrieval と internal-rag です。
Citation 必須にでき、明示 AI 分析へ証拠を渡します。
```

### 6. AWS / Kubernetes は？

```text
担当は Docker Compose とローカル/単機配備、Secret をイメージに入れない設計です。
フルマネージド K8s 運用まで担当したとは言いません。
```

### 7. この案件の弱い部分は？

```text
有料 LLM の既定検証、Billing UI、多テナント予算、SIEM/WORM、細粒度店舗 ACL です。
JWT/RBAC、Approval、PostgreSQL 永続化は既に実装済みです。
```

### 8. 現場に入ったら何から？

```text
権限と Audit、業務主鎖の E2E、Alembic とデータ境界、LLM コスト統治の順でキャッチアップします。
```
