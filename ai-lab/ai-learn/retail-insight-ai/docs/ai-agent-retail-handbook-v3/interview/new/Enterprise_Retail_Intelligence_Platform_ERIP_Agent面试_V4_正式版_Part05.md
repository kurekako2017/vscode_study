# Chapter 2　本番アーキテクチャ全体

## 2.1 全体構成

## 面接官

本番アーキテクチャを説明してください。

## 回答

代表構成は次です。

```text
利用者
 → CloudFront
 → ALB
 → Frontend（Nginx / 静的配信）
 → ALB / サービス経路
 → Backend（ECS Fargate 上の FastAPI）
 → RDS PostgreSQL
 → Secrets Manager / CloudWatch / IAM
```

S3 は成果物や静的資源の保管に使います。

## 追問

なぜこの構成か。

## 回答

マネージドサービス中心で運用負荷を抑えつつ、
可用性、セキュリティ、拡張性を確保するためです。

## Point

- 入口〜計算〜データ〜運用の一式

【面试技巧】

AWS は聞かれたら話す。开场不要主动展开。

---

## 2.2 可用性の考え方

## 面接官

高可用性をどう設計しますか。

## 回答

単一障害点を減らし、Multi-AZ の DB、複数タスクの API、
ヘルスチェックと自動置換、適切なタイムアウトとリトライを組み合わせます。

『サーバ一台で永久稼働』は前提にしません。

## 追問

100% 可用性と言えますか。

## 回答

言いません。目標を定義し、障害時の縮退と復旧を設計します。
正直さと設計の具体性が重要です。

## Point

- Multi-AZ / ヘルス / 自動復旧
- 過大表明しない

---

## 2.3 セキュリティ境界

## 面接官

インフラ面のセキュリティ要点は。

## 回答

最小権限 IAM、Secret の秘匿管理、HTTPS 終端、
セキュリティグループ、監査ログ、Backend での認証認可です。

ネットワークだけ、アプリだけ、のどちらか一方では不十分です。

## 追問

API キーを環境変数ベタ書きしますか。

## 回答

本番では Secrets Manager 等で管理し、必要最小限の注入にします。
リポジトリへ秘密情報を入れません。

## Point

- 多層防御
- Secret を dual 管理しない

# Chapter 3　Docker / デプロイ

## 3.1 なぜ Docker か

## 面接官

なぜ Docker を使いますか。

## 回答

実行環境を標準化し、開発・検証・本番の差分を減らすためです。

依存関係をイメージに固定し、デプロイ再現性を高めます。

## 追問

Docker があれば十分ですか。

## 回答

不十分です。オーケストレーション、設定管理、監視、権限、DB 運用が必要です。
コンテナは部品です。

## Point

- 環境標準化
- 部品であり全体ではない

---

## 3.2 イメージと実行

## 面接官

Backend / Frontend のコンテナ方針は。

## 回答

Backend は FastAPI 実行イメージ、Frontend は build した静的ファイルを Nginx で配信する形が基本です。

アプリ本体と実行環境を分離し、起動時に設定とマイグレーション方針を適用します。

## 追問

設定をイメージに焼き込みますか。

## 回答

秘密や環境差分は焼き込みません。実行時設定と Secret 注入で環境差を吸収します。

## Point

- 実行時設定
- Secret 非焼付

---

## 3.3 デプロイ手順の原則

## 面接官

デプロイで守る原則は。

## 回答

再現可能、ロールバック可能、ヘルスチェック通過後に切替、
DB マイグレーションの順序明確化です。

手作業の場当たり反映を避けます。

## 追問

失敗したら。

## 回答

新規を切り離し、旧版へ戻す、または修正版を再デプロイします。
状態とログを残して原因を固定します。

## Point

- 再現とロールバック

---

# Chapter 4　CI/CD

## 4.1 CI/CD の目的

## 面接官

CI/CD の目的は何ですか。

## 回答

品質ゲートを自動化し、安全に頻繁へ寄せるためです。

テスト、静的確認、イメージ build、デプロイ承認をパイプライン化します。

## 追問

テストが無い CD は。

## 回答

高速な事故配送になります。最低限の自動テストと検証をゲートに入れます。

## Point

- 品質ゲート
- 速さより安全性

---

## 4.2 パイプライン構成

## 面接官

パイプラインに何を入れますか。

## 回答

依存インストール、Backend/Frontend テスト、build、
セキュリティ基本チェック、成果物作成、環境へのデプロイです。

本番反映は権限と承認を分けます。

## 追問

誰でも本番デプロイできますか。

## 回答

できません。権限分離と監査可能な手順が必要です。

## Point

- 権限分離
- 本番は慎重に

---

# Chapter 5　Nginx / ALB / CloudFront

## 5.1 Nginx

## 面接官

Nginx の役割は。

## 回答

Frontend 静的配信、リバースプロキシ、基本的なルーティングやヘッダ制御です。
コンテナ内で Web サーバとして機能します。

## 追問

アプリサーバだけで良いのでは。

## 回答

静的配信とリバースプロキシを分離した方が運用と性能設計が明確です。

## Point

- 静的配信と proxy

---

## 5.2 ALB

## 面接官

なぜ ALB を使いますか。

## 回答

HTTPS 終端、負荷分散、ヘルスチェック、経路制御のためです。
Backend タスクの増減に対し、安定した入口を提供します。

## 追問

EC2 一台に直接公開では。

## 回答

単一障害点と運用負荷が増えます。可用性・運用性で不利です。

## Point

- 入口の標準化
- ヘルスチェック

---

## 5.3 CloudFront

## 面接官

CloudFront を使う理由は。

## 回答

静的資源の低遅延配信、キャッシュ、エッジでの保護・配信最適化です。
グローバルまたは広域利用者への体感改善に有効です。

## 追問

全部キャッシュして良いですか。

## 回答

いけません。認証付き API や個人応答は安易にキャッシュしません。
キャッシュ対象を設計します。

## Point

- 静的はキャッシュ
- 動的 API は慎重

---

# Chapter 6　S3 / RDS / ECS

## 6.1 S3

## 面接官

S3 の用途は。

## 回答

静的成果物、アップロードファイル、ビルド成果の保管などです。
耐久性が高く、オブジェクト保管の基本になります。

## 追問

DB に全部入れない理由は。

## 回答

大きなバイナリを RDB に抱えるとバックアップや性能設計が重くなります。
用途でストアを分けます。

## Point

- オブジェクト保管
- 用途分離

---

## 6.2 RDS PostgreSQL

## 面接官

RDS を選ぶ理由は。

## 回答

運用（バックアップ、パッチ、Multi-AZ 等）をマネージドで受けつつ、
PostgreSQL の業務特性を活かすためです。

アプリはコネクション、トランザクション、マイグレーションを正しく扱います。

## 追問

自前 EC2 に PostgreSQL では。

## 回答

可能ですが、運用負荷と可用性設計の責任が増えます。要件に応じてマネージドを優先します。

## Point

- マネージド運用
- アプリ側の正しい利用

---

## 6.3 ECS Fargate

## 面接官

なぜ ECS Fargate ですか。

## 回答

コンテナ実行をサーバ管理なしで行えるためです。

API をタスク単位でデプロイし、スケールと置換をしやすいです。
ERIP の API 中心構成に適合します。

## 追問

なぜ EC2 直接ではないか。

## 回答

OS パッチやキャパシティ管理の負荷が高いためです。
API サービス中心なら Fargate の方が運用負荷を抑えやすいです。

## Point

- サーバレスに近いコンテナ運用
- 運用負荷削減

---

## 6.4 スケーリング

## 面接官

スケールはどう考えますか。

## 回答

API タスク数、DB 性能、外部 LLM レート、検索負荷を分けて見ます。

アプリを増やすだけで DB や外部 API が詰まることがあるため、
ボトルネック単位で拡張します。

## 追問

オートスケールだけすれば良いですか。

## 回答

不十分です。状態、接続数、コスト、コールドスタート的遅延も設計対象です。

## Point

- ボトルネック単位
- 盲目的スケール禁止

---

# Chapter 7　IAM / Secrets / CloudWatch

## 7.1 IAM

## 面接官

IAM 設計の原則は。

## 回答

最小特権です。役割ごとに必要な操作だけ許可します。

アプリ実行ロール、デプロイロール、人の管理ロールを混同しません。

## 追問

強い権限を共有する問題は。

## 回答

事故と内部不正の影響範囲が最大化します。分離と監査が必要です。

## Point

- 最小特権
- ロール分離

---

## 7.2 Secrets

## 面接官

Secret 管理はどうしますか。

## 回答

API キーや DB パスワードは Secrets Manager 等で管理し、
実行時に注入します。Git 管理やイメージ焼付を禁止します。

## 追問

ローテーションは。

## 回答

可能なら定期ローテーションと影響範囲の最小化を設計します。
突然無効化されても安全に失敗する方が、漏洩放置より良いです。

## Point

- Secret をリポジトリに置かない

---

## 7.3 CloudWatch

## 面接官

監視で何を見ますか。

## 回答

API レイテンシ、エラー率、タスク健全性、DB 接続/CPU、
ログの error 集約、必要なら業務メトリクスです。

見えない障害は復旧できません。

## 追問

ログを全部永久保存しますか。

## 回答

コストと法令要件を踏まえ保持期間を決めます。
機密がログに出ない設計が前提です。

## Point

- 可観測性
- 保持期間と機密

---

# Chapter 8　企業上線

## 8.1 上線前チェック

## 面接官

本番上線前に何を確認しますか。

## 回答

認証認可、主要業務フロー、マイグレーション、バックアップ、
ロールバック手順、監視アラート、Secret、負荷の基本確認です。

『動いた』だけでなく『止められる・戻せる・見える』を確認します。

## 追問

一番忘れやすいのは。

## 回答

ロールバックと監視です。前進手順だけ整備して失敗時が空白になりがちです。

## Point

- 進める・戻す・見える

---

## 8.2 運用インシデント

## 面接官

障害対応の基本は。

## 回答

影響範囲特定、止血、原因固定、復旧、再発防止です。
request_id やデプロイ版、DB 状態、外部依存を順に見ます。

## 追問

顧客への説明は。

## 回答

推測で語らず、確定事実と暫定対策、次の更新タイミングを伝えます。

## Point

- 止血 → 固定 → 再発防止

# Chapter 9　クロージング

## 9.1 1分で本番構成

## 面接官

本番構成を 1 分で説明してください。

## 回答

CloudFront と ALB を入口に、Frontend は Nginx 静的配信、
Backend は ECS Fargate の FastAPI、データは RDS PostgreSQL です。
Secret は Secrets Manager、監視は CloudWatch、権限は IAM 最小特権。
Docker と CI/CD で再現可能にデプロイします。

## Point

- 入口・計算・データ・運用を一通り

# Chapter 10　ネットワークとデータ保護

## 10.1 通信経路

## 面接官

通信経路のセキュリティを説明してください。

## 回答

利用者から入口までは HTTPS を前提とし、
ALB で終端、内部は必要最小限の通信だけを許可します。

不要なポート公開、管理ポートのインターネット露出を避けます。

## 追問

内部通信は無防備で良いですか。

## 回答

良くありません。少なくともネットワーク分割と最小権限、
重要サービスの認証を維持します。

## Point

- HTTPS 前提
- 最小公開

---

## 10.2 データ保護

## 面接官

データ保護で何をしますか。

## 回答

保存データの暗号化（RDS/S3 等の標準機能）、
アクセス制御、バックアップ、監査です。

加えてアプリ層で RBAC とマスキング方針を持ちます。
インフラ暗号化だけで業務権限は代替できません。

## 追問

バックアップの意味は。

## 回答

障害や誤削除からの復旧手段です。
取得だけでなくリストア手順の確認が重要です。

## Point

- 暗号化 + 権限 + バックアップ
- リストアまで含めて設計

---

# Chapter 11　コストと性能

## 11.1 コスト管理

## 面接官

クラウドコストで注意した点は。

## 回答

常時最大構成に固定しないこと、
ログ過保管、不要リソース放置、
LLM 呼び出しの無駄を避けることです。

観測してから縮小/拡大します。

## 追問

安い構成が最良ですか。

## 回答

可用性やセキュリティを壊す安さは最良ではありません。
要件を満たす最小コストを狙います。

## Point

- 観測に基づく最適化
- 安さより要件適合

---

## 11.2 性能の見方

## 面接官

性能問題をどう切り分けますか。

## 回答

フロント、ALB、API、DB、外部 LLM、検索を段階で測ります。

全体が遅い時にアプリだけ増やすと、DB や外部 API が先に壊れます。
レイテンシ内訳が先です。

## 追問

キャッシュは使いますか。

## 回答

静的資源や更新頻度の低い参照は有効です。
権限付き個別応答は安易にキャッシュしません。

## Point

- 内訳計測
- キャッシュ対象を選ぶ

# Chapter 12　ECS と RDS の運用細節

## 12.1 ヘルスチェック

## 面接官

ヘルスチェックをどう設計しますか。

## 回答

プロセス生存だけでなく、重要依存の readiness を分けて考えます。

起動中と準備完了を混同すると、未準備タスクへトラフィックが入り障害になります。

## 追問

/health と /ready の違いは。

## 回答

health は生存、ready はリクエストを受けてよいかです。
DB 未接続なら ready を落とす、などの使い分けをします。

## Point

- liveness と readiness を分ける

---

## 12.2 マイグレーション運用

## 面接官

本番 DB マイグレーションの注意点は。

## 回答

後方互換、実施順序、失敗時方針、ロック時間です。

アプリ新版が旧スキーマでも一時的に動くか、
逆に旧アプリが新スキーマで壊れるかを確認します。

## 追問

アプリと同時に強変更して良いですか。

## 回答

可能な限り段階的にします。
一気の破壊的変更はロールバックを困難にします。

## Point

- 段階的変更
- 戻し方を先に決める

# Chapter 13　面接での AWS の話し方

## 13.1 話す順序

## 面接官

AWS 構成を聞かれたら何から話しますか。

## 回答

まず利用者入口、次に Frontend/Backend、次に DB、最後に運用（IAM/Secret/監視）です。

サービス名の羅列から入ると、設計意図が伝わりません。

## 追問

ECS の詳細設定から始めて良いですか。

## 回答

最初は避けます。全体像の後に、聞かれた詳細へ降りていきます。

## Point

- 全体 → 詳細
- 意図を先に

---

## 13.2 やりすぎ表現を避ける

## 面接官

実績以上に大きく見せてしまう危険は。

## 回答

あります。過大表明は信頼を失います。

実装した構成、運用した範囲、設計した内容を分けて正直に話します。
ただし本教材では完成案件として、担当範囲を明確に語ります。

## 追問

分からないことを聞かれたら。

## 回答

知らない部分は認め、調べ方と設計原則で答えます。
適当な断定はしません。

## Point

- 正直さと原則
- 断定しすぎない

---


# Part 05 要点总结

1. 入口：CloudFront / ALB / Nginx
2. 計算：ECS Fargate + FastAPI
3. データ：RDS PostgreSQL（+ 必要に応じ S3）
4. 運用：IAM 最小特権、Secrets、CloudWatch
5. 配送：Docker + CI/CD + ロールバック
6. 可用性：Multi-AZ、ヘルスチェック、単一障害点削減

AWS は聞かれたら話す。案件开场では業務価値を優先する。
