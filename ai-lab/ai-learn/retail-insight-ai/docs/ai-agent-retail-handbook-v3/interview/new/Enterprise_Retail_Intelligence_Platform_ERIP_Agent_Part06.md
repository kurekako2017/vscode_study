# Chapter 4B　LangChain / LangGraph 压迫问答

## 4B.1 なぜ LangChain を使用しましたか

## 面接官

なぜ LangChain を使用しましたか。

## 回答

プロンプト（プロンプト（Prompt））、リトリーバー（リトリーバー（Retriever））、RAG コンテキスト（RAG コンテキスト（コンテキスト（Context）））、引用情報（引用情報（Citation））、ツール（ツール）、
LLM（大規模言語モデル）（大規模言語モデル） 連携（LLM 連携） など AI コンポーネント を
統一的に構成するためです。

ERIP では、
単発の LLM 呼び出しではなく、
根拠取得から構造化出力までの AI コンポーネントを
LangChain で組み立てています。

## Point

- LangChain ＝ AI コンポーネント

---

## 4B.2 なぜ LangGraph を使用しましたか

## 面接官

なぜ LangGraph を使用しましたか。

## 回答

ステート（ステート（State））、ノード、エッジ（エッジ（Edge））、条件分岐を用いて、
複数ステップの エージェントワークフロー（Agent ワークフロー（ワークフロー（Workflow））） を制御するためです。

経営分析は route / KPI / research / report の多段階であり、
状態付きフロー制御が必要でした。

## Point

- LangGraph ＝ ステートフル・エージェントワークフロー（ステートフル・エージェントワークフロー（Stateful エージェントワークフロー（Agent ワークフロー）））

---

## 4B.3 違いは

## 面接官

LangChain と LangGraph の違いは何ですか。

## 回答

LangChain は、
プロンプト、リトリーバー、RAG コンテキスト、
引用情報、ツール、LLM 連携 など
AI コンポーネント を構成する フレームワーク（フレームワーク（Framework）） です。

LangGraph は、
ステート、ノード、エッジ、条件分岐を用いて
複数ステップの エージェントワークフロー を
制御する フレームワークです。

ERIP では、
LangChain で各 AI 処理を構成し、
LangGraph で全体 ワークフロー を制御しています。

## Point

- コンポーネント vs ワークフロー

---

## 4B.4 なぜ両方必要か

## 面接官

なぜ両方必要ですか。

## 回答

AI コンポーネントだけでは業務フローを安全に制御できず、
ワークフロー だけでは各ステップの AI 能力が不足するためです。

ERIP は両者協働の エンタープライズ AI エージェント基盤（エンタープライズ AI エージェント基盤（Enterprise AI Agent Platform）） です。

## 追問

LangChain だけでは駄目ですか。LangGraph だけでは。

## 回答

LangChain だけでは、
単発 RAG や チェーン（チェーン） は作れても、
多段階の状態管理と分岐が弱くなります。

LangGraph だけでは、
ワークフロー の器は作れても、
プロンプト / リトリーバー / RAG / LLM 部品の統合が曖昧になります。

両方必要です。

## Point

- 片方では Enterprise Agent にならない

---

## 4B.5 どこで使うか

## 面接官

ERIP のどこで LangChain を使い、どこで LangGraph を使いますか。

## 回答

LangChain：
文書 / チャンク（チャンク） / リトリーバー / プロンプト / コンテキスト / 引用情報 / LLM 連携。

LangGraph：
START → route → kpi / research → report → END の
エージェントワークフロー 制御（制御）。

責任境界は、
LangChain ＝ AI コンポーネント、
LangGraph ＝ ステートフルワークフロー（Stateful ワークフロー） です。

## Point

- 位置を図で指せる

---

## 4B.6 自作しなかった理由

## 面接官

フレームワーク を使わず自作しなかった理由は。

状態管理、分岐、部品統合、説明可能性、保守性を

LangChain と LangGraph を使い、
ERIP 固有の業務ルール・権限・承認・監査 を
その上に構築する方が適切でした。

## Point

- 自作は可能だが、企業保守で不利になりやすい

# Chapter 2　日本 AI Agent 面接の戦い方

## 2.1 評価ポイント

## 面接官

日本の AI Agent 面接で何を見られますか。

## 回答

主に次です。

1. 業務課題を理解しているか
2. なぜその技術を選んだか
3. 権限・承認・監査まで設計できるか
4. 失敗時の説明ができるか
5. 日本語で簡潔に構造化して話せるか

モデル名の知識量だけでは評価されません。

## 追問

一番落とされやすい点は。

## 回答

技術羅列だけで業務価値が語れないこと、
未完成を隠すこと、認証と認可の混同、RAG を魔法扱いすることです。

## Point

- 業務 → 設計 → 実装 → 運用
- 日本語の構造化

【面试技巧】

先结论，后展开，最后落边界。

## 面接官

回答の型はありますか。

## 回答

あります。

```text
結論

 → 注意点
```

- 結論先出し
- 追問余地を残す

# Chapter 3　TL 压迫问答

## 3.1 それは本当に完成か

## 面接官

それは本当に本番で使える完成形ですか。未完成を隠していませんか。

## 回答

完成した企業向けプラットフォームとして、
文書管理、RAG、分析、レポート、承認、監査、JWT（JSON Web Token）（JSON Web トークン）/RBAC（ロールベースアクセス制御）（ロールベースアクセス制御） まで一連で実装しています。

検証用の stub モードやテスト用 InMemory はありますが、
それは品質確保の手段であり、正式業務経路の代替ではありません。
正式データは PostgreSQL、権限と監査がある状態で業務フローが通ります。

## 追問

では弱点は何ですか。

## 回答

外部モデル品質のばらつき、検索チューニングの継続、
運用面でのコスト最適化は継続課題です。
ただし中核業務フローとガバナンスは成立しています。

## Point

- 完成範囲を明確に
- 弱点は正直に、ただし核心は守る

【容易说错】

『其实还没做完』と自分から崩さない。范围を明確に语る。

---

## 3.2 なぜ Agent と呼ぶ

## 面接官

ただの API では。なぜ Agent と言うのですか。

## 回答

単一応答 API ではなく、目標に対して複数ステップを実行し、
ツール（検索・分析・生成）を使い、状態を持って業務を進めるためです。

ただし無制御の自律エージェントではなく、
権限・ワークフロー・承認 で制御された Agentic システムです。

## 追問

過剰な言い過ぎでは。

## 回答

『完全自律の万能 Agent』とは言いません。
業務上の Agent 的ワークフローを実装した、と正確に話します。

## Point

- 制御された エージェント型ワークフロー（Agentic ワークフロー）
- 誇張しない

---

## 3.3 事故が起きたら

## 面接官

誤った経営レポートが出たら誰の責任ですか。システムは何をしますか。

## 回答

業務確定の責任分界は承認者にあります。

システムは、根拠 引用情報、版管理、承認履歴、監査ログを提供し、
誰が何に基づき承認したかを追跡可能にします。
無審査確定を防ぐのが設計目的です。

## 追問

システムに責任は無いのですか。

## 回答

品質と制御を提供する責任はあります。
だから 検索処理（検索処理（Retrieval）） 品質、権限、状態機械、監査を実装しています。
『AI が書いたから不可避』とは言いません。

## Point

- 人の責任分界 + システムの制御責任

---

## 3.4 コスト爆発

## 面接官

LLM コストが爆発したらどうしますか。

## 回答

用途別ルーティング、不要呼び出し削減、
キャッシュ可能な前処理、利用量 Ledger、予算/モード制御で抑えます。

すべてを最高品質モデルへ固定しないことが基本です。

## 追問

止められない呼び出しは。

## 回答

管理権限でモード制御や kill switch 的な運用手段を持ち、
異常時に安全側へ倒します。

## Point

- 用途分離
- 観測と制御

---

## 3.5 情報漏洩

## 面接官

社内文書が外部に漏れるリスクをどう抑えますか。

## 回答

JWT/RBAC、検索時 ACL（アクセス制御リスト）、ログ秘匿、シークレット（シークレット） 管理、
最小権限、監査で抑えます。

また、不要な全文を外部へ送らない、プロンプト/ログに機密を出さない方針です。

## 追問

完璧に防げますか。

## 回答

リスクをゼロとは言いません。多層防御と検知、権限最小化で実用安全を作ります。

## Point

- 多層防御
- ゼロ断言しない

---

## 3.6 なぜあなたが必要か

## 面接官

ライブラリを繋げば誰でも作れるのでは。

## 回答

部品を繋ぐことと、企業業務として成立させることは別です。

権限、承認、監査、状態機械、失敗処理、運用、説明責任まで含めて
設計・実装できることが価値です。

ERIP はその全体を通した実装です。

## 追問

あなたの強みは。

## 回答

業務理解と バックエンド 設計、AI コンポーネントの統制、日本語での設計説明です。
特定ライブラリ暗記だけではありません。

## Point

- 部品接続 ≠ 企業システム

# Chapter 4　技術比較

## 4.1 なぜ Spring Boot ではないか

## 面接官

なぜ Spring Boot で作らなかったのですか。

## 回答

Spring Boot は企業 Java で非常に強い選択です。

今回は AI/RAG/Python エコシステムとの統合速度、
Pydantic 契約、ワークフロー 実装を優先し FastAPI を選びました。
Java 案件では Spring を選びます。否定ではありません。

## 追問

Spring の経験は。

## 回答

Java/Spring 系の業務経験があります。
今回の AI プラットフォーム要件に FastAPI が適合した、という話です。

## Point

- 否定せず適合性
- 案件で選ぶ

【面试技巧】

永远先肯定 Spring 的企业价值。

---

## 4.2 Java と比較

## 面接官

Java と Python のどちらが企業向きですか。

## 回答

どちらも企業向きです。領域次第です。

大規模基幹、厳格な型と長期保守のチーム標準なら Java が強いことが多いです。
AI 周辺と高速な API 統合では Python が強いことが多いです。
ERIP は後者の中心課題が強かったため Python です。

## 追問

混在はあり得ますか。

## 回答

あり得ます。基幹は Java、AI サービスは Python、など境界を分けて連携します。

## Point

- 銀の弾丸なし
- 境界設計

---

## 4.3 なぜ Django ではないか

## 面接官

なぜ Django ではないのですか。

## 回答

Django は強力なフルスタック枠です。

ERIP は React を フロントエンド（フロントエンド）、API を バックエンド とし、
RAG/ワークフロー を明確なサービス境界で置く必要がありました。
API 中心 + AI 統合には FastAPI が適合しました。

## 追問

管理画面がある Django の利点は。

## 回答

管理機能を早く出す案件では利点大です。
今回の中心は企業 API と AI 業務流でした。

## Point

- 要件適合で選択

---

## 4.4 なぜ ノード ではないか

## 面接官

なぜ ノード.js ではないのですか。

## 回答

ノード も API に強いです。

ただし今回の中心課題は RAG、エンベディング（エンベディング（Embedding））、Python AI 周辺との統合でした。
チームとライブラリ資産を含めて Python/FastAPI を選択しました。

## 追問

フロントエンド が React なら バックエンド も ノード では。

## 回答

同言語の利点はあります。ただし AI 実装効率とのトレードオフで Python を優先しました。

## Point

- 同言語利点 vs AI 効率

## 4.5 なぜ ChatGPT 単体ではないか

## 面接官

なぜ ChatGPT をそのまま使わないのですか。

## 回答

ChatGPT は優秀な汎用 AI です。

しかし社内文書の権限付き管理、根拠固定、承認、監査、業務フロー統合は
別途システムが必要です。

ERIP はそれらを含む企業プラットフォームです。

## 追問

ChatGPT を批判しますか。

## 回答

しません。用途が違います。汎用対話と企業業務基盤は役割が異なります。

## Point

- 汎用 AI vs 企業 Platform

【容易说错】

『ChatGPT は使えない』は失分。

## 4.6 なぜ RAG が必要か

## 面接官

なぜモデルを追加学習せず RAG ですか。

## 回答

社内文書は更新が頻繁で、権限や出典情報管理が必要だからです。

毎回学習し直すより、検索で最新根拠を渡す方が運用適合しやすいです。
必要に応じて学習手法は併用し得ますが、第一選択を RAG にしました。

## 追問

RAG の限界は。

## 回答

検索が弱いと回答も弱いです。だから チャンク、Hybrid、評価が重要です。

## Point

- 更新・権限・出典情報に強い
- 検索品質が前提

---

## 4.7 なぜ 承認 / 監査 か

## 面接官

AI が正しいなら 承認 は不要では。

## 回答

AI は誤り得ます。経営資料は影響が大きいです。

生成と業務確定を分け、人の責任分界を残すために 承認 が必要です。
監査 は後からの説明責任を支えます。

## 追問

開発速度が落ちませんか。

## 回答

落ちる部分はありますが、企業信用を買うコストです。
速度だけ最適化して事故る方が損失が大きいです。

## Point

- 責任分界
- 速度より信用

## 5.4 連続4

## 4B.4 なぜ両方必要か

AI コンポーネントだけでは業務フローを安全に制御できず、
ワークフロー だけでは各ステップの AI 能力が不足するためです。

ERIP は両者協働の エンタープライズ AI エージェント基盤 です。

## 追問

## 回答

LangChain だけでは、
単発 RAG や チェーン は作れても、
多段階の状態管理と分岐が弱くなります。

LangGraph だけでは、
ワークフロー の器は作れても、
プロンプト / リトリーバー / RAG / LLM 部品の統合が曖昧になります。

両方必要です。

## 6.2 三分紹介

## 回答

従来は資料が分散し、分析とレポート作成に時間が掛かり、根拠説明も困難でした。

ERIP は LangChain と LangGraph を中核とした エンタープライズ AI エージェント基盤 です。
