# Chapter 2　LangGraph / Workflow 基礎

## 2.1 なぜ Workflow が必要か

## 面接官

なぜ Workflow が必要ですか。

## 回答

経営分析や承認は単発関数では表現しきれない多段処理だからです。

状態を持ち、順序と分岐を明示し、途中結果を追跡できる必要があります。
Workflow により業務プロセスを可視化・テスト可能にします。

## 追問

普通の Service メソッド連鎖では駄目ですか。

## 回答

小規模なら可能です。ただし状態遷移、条件分岐、再開、監査点が増えると、
暗黙の呼び出し連鎖は破綻しやすいです。Workflow はそれを明示化します。

## Point

- 多段業務の明示化
- 状態と順序を可視化

---

## 2.2 LangGraph とは

## 面接官

LangGraph をどう使いましたか。

## 回答

状態付きグラフとして業務ステップを Node と Edge で表現するために使いました。

分析ワークフローなど、段階的に状態を更新する処理で有効です。
『エージェントが勝手に何でもする』ためではなく、制御可能な業務流のために使います。

## 追問

なぜ選んだのですか。

## 回答

State、Node、条件分岐をコードとして明示でき、
複雑化した分析フローを保守しやすかったためです。

## Point

- State + Node + Edge
- 制御可能な業務流

【学习提示】

LangGraph は『自由放任 Agent』ではなく『制御された状態機械』として語る。

---

## 2.3 State とは

## 面接官

Workflow の State とは何ですか。

## 回答

各 Node が読み書きする共有状態です。

タスク ID、入力条件、中間分析結果、エラー情報、完了フラグなどを保持します。
State があるから途中経過を説明・再開・監査できます。

## 追問

State に何でも入れて良いですか。

## 回答

いけません。巨大な生データや機密を無制限に載せると危険です。
業務に必要な最小限と参照 ID を中心にします。

## Point

- 共有状態
- 最小限を保持

---

## 2.4 Node と Edge

## 面接官

Node と Edge を説明してください。

## 回答

Node は処理単位（例：KPI 集計、調査結果統合、レポート生成）です。
Edge は遷移、条件付き Edge は分岐です。

各 Node は入力 State、出力 State、副作用（保存やイベント）を明確にします。

## 追問

巨大 Node の問題は。

## 回答

テスト困難で失敗原因が不明になります。責務単位で分割します。

## Point

- Node = 処理
- Edge = 遷移

---

# Chapter 3　Analysis / Report Workflow

## 3.1 Analysis Workflow

## 面接官

分析 Workflow の流れを説明してください。

## 回答

代表的には次です。

```text
入力受付
 → 権限・前提チェック
 → データ/根拠収集
 → 分析 Node
 → 結果整形
 → レポート素材生成
 → 完了 / 失敗
```

各段階で State を更新し、失敗時は理由を残します。

## 追問

どこが AI でどこが決定的処理ですか。

## 回答

集計や状態遷移は決定的、文章化や高度要約は LLM 経路、
根拠収集は Retrieval です。全部を LLM に任せません。

## Point

- 段階的 State 更新
- AI と決定処理を混在させすぎない

---

## 3.2 Report Workflow

## 面接官

レポート生成 Workflow を説明してください。

## 回答

分析結果と根拠を入力に、取締役会向けレポートを生成し、
Report / ReportVersion として保存します。

生成完了は『下書き的成果物の確定』であり、業務上の最終公開とは別です。
最終化は Approval を経ます。

## 追問

なぜ Version が必要ですか。

## 回答

差戻し後の再生成や、どの版を承認したかを追跡するためです。
上書き一発だと監査が壊れます。

## Point

- 生成 ≠ 最終公開
- Version で追跡

---

## 3.3 失敗と再開

## 面接官

Workflow 失敗時はどうしますか。

## 回答

失敗 Node と理由を State / ログに残し、タスクを failed 等へ遷移します。
可能な場合は安全な地点から再実行します。

中途半端な成功データを『完了』扱いしません。

## 追問

途中結果は残しますか。

## 回答

調査に必要な範囲で残します。ただし不完全成果物が正規レポートとして流通しないよう状態で隔離します。

## Point

- 失敗を隠さない
- 状態で隔離

---

# Chapter 4　Approval / Audit

## 4.1 なぜ Approval が必要か

## 面接官

なぜ Approval が必要ですか。

## 回答

AI 生成物を無審査で確定すると、誤った経営判断資料が流通するリスクがあるためです。

企業では影響の大きい成果物に人の責任分界が必要です。
Approval により『生成』と『業務確定』を分離します。

## 追問

全部自動承認では。

## 回答

速度は上がっても説明責任が消え、事故時に誰も止められません。
重要成果物は人の確認を残します。

## Point

- 生成と確定を分離
- 責任分界

【容易说错】

Approval を『将来やる』と言わない。完成機能として説明する。

---

## 4.2 Approval 状態遷移

## 面接官

Approval の状態を説明してください。

## 回答

代表的には提出（pending）→ 承認（approved）/ 差戻し（rejected 等）→ 必要なら再提出です。

不正な遷移（承認済みの再承認など）は拒否します。
操作者ロールも検証します。

## 追問

Task 完了と Approval 完了は同じですか。

## 回答

違います。Task 完了は処理終了、Approval 完了は業務上の承認完了です。
混同するとガバナンスが崩れます。

## Point

- 状態機械を厳密に
- Task 完了 ≠ 承認完了

---

## 4.3 Audit の役割

## 面接官

Audit は何を記録しますか。

## 回答

誰が、いつ、何を、どの対象に、どんな結果で行ったかです。

文書登録、検索、分析、承認、権限変更、AI Runtime 変更などが対象です。
後から説明できることが目的です。

## 追問

ログがあれば Audit 不要ですか。

## 回答

アプリログと Audit は目的が違います。
Audit は業務監査に耐える操作事実の記録として設計します。

## Point

- Who / When / What / Result
- 業務監査向け

---

## 4.4 Approval と Audit の一体性

## 面接官

承認と監査の関係は。

## 回答

承認成功時に監査が欠落すると、責任追跡ができません。
状態更新と監査記録をセットで残す設計にします。

## 追問

拒否も記録しますか。

## 回答

重要操作では記録します。『何が通ったか』だけでなく『何を止めたか』も価値があります。

## Point

- 承認と監査はセット

---

# Chapter 5　SSE / Streaming / Background

## 5.1 なぜ SSE か

## 面接官

なぜ SSE を使いますか。

## 回答

長時間の分析タスク進捗を、Frontend がリアルタイムに受け取るためです。

ポーリングだけでも可能ですが、進捗イベントを押し出す方が UX と実装意図が明確です。
完了・失敗・中間状態をイベントとして送れます。

## 追問

WebSocket では。

## 回答

双方向が必須なら候補です。進捗配信中心なら SSE で十分なケースが多いです。

## Point

- 進捗のリアルタイム通知
- 用途で選ぶ

---

## 5.2 SSE イベント設計

## 面接官

SSE で送るイベントは何ですか。

## 回答

例：accepted、progress、completed、error などです。

重要な規則は、error 後に成功 done を送らない、矛盾イベントを出さないことです。
Frontend はイベントに応じて loading / error / completed を更新します。

## 追問

イベントに何を載せますか。

## 回答

task_id、status、必要最小限の進捗情報。機密全文や巨大中間物は載せません。

## Point

- 矛盾イベント禁止
- 最小情報

---

## 5.3 BackgroundTasks

## 面接官

BackgroundTasks の役割は。

## 回答

HTTP 応答を先に返し、重い処理を背後で進めるためです。

分析開始 API が何分もブロックすると UX とタイムアウト問題が起きます。
受付と実行を分離します。

## 追問

完全なジョブキューと同じですか。

## 回答

思想は近いですが、規模と要件で実装が異なります。
ERIP ではタスク状態を Repository に持ち、進捗を SSE 等で伝えます。

## Point

- 受付と実行の分離

---

## 5.4 Event の意義

## 面接官

Event を残す意義は何ですか。

## 回答

状態変化を後から追跡し、Frontend 表示や運用調査に使うためです。

『今どこか』が分からない非同期処理は、企業 UX として不合格です。

## 追問

Event と Audit の違いは。

## 回答

Event は進行通知・状態変化の伝達、Audit は監査可能な操作事実です。
重なりますが目的が違います。

## Point

- 非同期でも可視化
- Event ≠ Audit

---

# Chapter 6　ERIP 完全業務フロー

## 6.1 端到端フロー

## 面接官

ERIP の完全業務フローを説明してください。

## 回答

```text
ログイン（JWT/RBAC）
 → 文書登録 / Import / Chunk
 → RAG 検索で根拠取得
 → 分析 Workflow 実行
 → レポート生成（ReportVersion）
 → Approval 提出
 → 承認 / 差戻し
 → Audit で全履歴追跡
```

必要に応じて Frontend は SSE で進捗を表示します。

## 追問

一番重要な分岐は。

## 回答

生成後に Approval へ進む点です。ここで人とシステムの責任が接続されます。

## Point

- 端到端を暗記
- Approval が要所

---

## 6.2 主鎖と副鎖

## 面接官

主業務と副次業務をどう分けて説明しますか。

## 回答

主鎖は文書→RAG→分析→レポート→承認→監査です。
KPI タスク分析や学習用画面は説明補助になり得ますが、主価値は主鎖です。

面接では主鎖を先に完成形で話します。

## 追問

全部を同じ比重で話すと。

## 回答

論点が散り、何のシステムか伝わりません。主鎖優先です。

## Point

- 主鎖優先

【面试技巧】

先讲主链，辅线被问再展开。

---

## 6.3 失敗パターン

## 面接官

業務フローで特に警戒する失敗は。

## 回答

権限漏れ、根拠なし生成、承認スキップ、監査欠落、状態不整合、
長時間処理の無応答です。

それぞれを設計で防ぎ、テストで固定します。

## 追問

無応答をどう防ぐか。

## 回答

非同期化、タイムアウト、進捗イベント、失敗状態の明示です。

## Point

- 失敗モードを先に設計

---

# Chapter 7　TL 深掘り

## 7.1 Agent と Workflow

## 面接官

これは Autonomous Agent ですか。

## 回答

目的は自律放任ではなく、企業業務を安全に進める Agentic Workflow です。

ツールや LLM を使っても、状態・権限・承認・監査で制御します。
『何でも自動』より『責任ある自動化』です。

## 追問

Agent という言葉をどう使いますか。

## 回答

役割分担された処理主体として使い、魔法の黒箱としては使いません。
面接では実装境界を具体的に話します。

## Point

- 責任ある自動化
- 黒箱にしない

---

## 7.2 テスト観点

## 面接官

Workflow をどうテストしますか。

## 回答

Node 単体、状態遷移、失敗経路、権限不足、Approval 不正遷移、
SSE イベント順序などをテストします。

成功経路だけでなく、止めるべき操作が止まるかを重視します。

## 追問

なぜ失敗経路が重要か。

## 回答

企業システムは『うまく動く』より『危険な操作を止める』が信用になるためです。

## Point

- 成功より停止条件
- 状態遷移テスト

---

# Chapter 8　クロージング

## 8.1 2分説明

## 面接官

Workflow 周りを 2 分で説明してください。

## 回答

ERIP では分析とレポートを Workflow で段階実行し、State で進捗を管理します。
生成したレポートは Approval で人の確認を経て確定し、操作は Audit に残します。
長時間処理は Background 実行し、SSE で進捗を Frontend に届けます。
目的は自律放任ではなく、説明可能で責任分界のある業務自動化です。

## Point

- Workflow + Approval + Audit + SSE

# Chapter 9　Node 設計の実践

## 9.1 良い Node の条件

## 面接官

良い Node 設計の条件は何ですか。

## 回答

入力と出力が明確で、副作用が説明可能で、単体テストできることです。

1 Node が『分析全部』を抱え込むと、失敗原因も改善点も見えなくなります。
小さく、意味のある業務ステップに分けます。

## 追問

副作用とは何ですか。

## 回答

DB 保存、外部 API 呼び出し、イベント発行など、State 更新以外の影響です。
副作用は隠さず、どこで起きるかを設計に明示します。

## Point

- 入出力明確
- 副作用を隠さない
- テスト可能な粒度

---

## 9.2 条件分岐の置き方

## 面接官

条件分岐はどこに置きますか。

## 回答

業務ルールに基づく分岐は Workflow の条件 Edge または専用判定 Node に置きます。

散在した if を Service 各所に置くと、全体フローが読めなくなります。
『どの状態のとき次へ進むか』を一箇所で説明できるようにします。

## 追問

権限チェックも Workflow 内だけで良いですか。

## 回答

いいえ。API 入口の認可は必須です。
Workflow 内は追加の業務条件であり、入口制御の代替ではありません。

## Point

- 分岐を可視化
- 入口認可は別途必須

# Chapter 10　Report と人の責任

## 10.1 取締役会レポートの要件

## 面接官

取締役会向けレポートで特に重要な要件は何ですか。

## 回答

正確性、根拠、責任者、改訂履歴です。

読みやすさだけでは不十分で、
『何に基づき、誰が承認した版か』が追える必要があります。

## 追問

AI が書いた文章の責任は誰にありますか。

## 回答

業務上は承認者が最終責任分界を持ちます。
だからこそ Approval を省略できません。
システムは根拠提示と履歴で支援します。

## Point

- 根拠と版と承認者
- AI は支援、確定は人

---

## 10.2 差戻し後の流れ

## 面接官

差戻し後はどうなりますか。

## 回答

差し戻し理由を残し、修正・再生成の後に再提出します。
旧版と新版を区別し、どれが現行候補かを状態で管理します。

上書き消失すると、何が却下されたか分からなくなります。

## 追問

差戻し理由は誰が見ますか。

## 回答

提出者と承認関係者です。監査上も重要な記録になります。

## Point

- 差戻しは履歴付き
- 版を消さない

---

# Chapter 11　SSE 実装の注意

## 11.1 再接続と重複

## 面接官

SSE 切断時はどうしますか。

## 回答

Frontend は再接続し、最新タスク状態を API で再取得して整合させます。
イベントだけに依存して状態を推測し続けないことが重要です。

## 追問

同じ完了イベントが二重に来たら。

## 回答

Frontend と Backend の双方で冪等に扱います。
すでに completed なら表示を壊さないようにします。

## Point

- イベント + 状態再取得
- 冪等な表示更新

---

## 11.2 error 後の done 禁止

## 面接官

なぜ error 後に done を送ってはいけないのですか。

## 回答

Frontend の最終状態が矛盾するからです。

エラー表示の後に成功完了が出ると、利用者はどちらを信じてよいか分かりません。
最終イベントの意味を厳密に定義します。

## 追問

部分成功はどう表現しますか。

## 回答

曖昧な成功にせず、状態を明示します。
例：一部処理済みだが業務完了ではない、など。
必要なら専用ステータスを使います。

## Point

- 最終状態を矛盾させない
- 部分成功を曖昧にしない

---

# Chapter 12　面接用ストーリー

## 12.1 失敗から学んだ点

## 面接官

この領域で苦労した点は何ですか。

## 回答

長時間処理の『今どこか分からない』問題と、
生成完了を最終確定と誤解する設計リスクでした。

SSE と状態 API の併用、Approval 分離、Audit 徹底で解決しました。

## 追問

同じ失敗をどう防ぎますか。

## 回答

状態機械テスト、イベント契約テスト、権限不足テストを最初から入れます。
成功経路だけ満足しないことです。

## Point

- 可視化と責任分界
- 失敗経路をテストする

---


# Part 04 要点总结

1. Workflow は多段業務の状態と順序を明示する
2. LangGraph は制御可能な State 機械として使う
3. レポート生成 ≠ 業務確定。Approval が責任分界
4. Audit は Who/When/What/Result を残す
5. SSE は長時間処理の進捗可視化
6. 主鎖：文書 → RAG → 分析 → レポート → 承認 → 監査

『自動で何でもやる』ではなく『責任ある自動化』で語る。
