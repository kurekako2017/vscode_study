# Chapter 2　日本 AI Agent 面接の戦い方

## 2.1 評価ポイント

## 面接官

日本の AI Agent 面接で何を見られますか。

## 回答

主に次です。

1. 業務課題を理解しているか
2. なぜその技術を選んだか
3. 権限・承認・監査まで設計できるか
4. 失敗時の説明ができるか
5. 日本語で簡潔に構造化して話せるか

モデル名の知識量だけでは評価されません。

## 追問

一番落とされやすい点は。

## 回答

技術羅列だけで業務価値が語れないこと、
未完成を隠すこと、認証と認可の混同、RAG を魔法扱いすることです。

## Point

- 業務 → 設計 → 実装 → 運用
- 日本語の構造化

【面试技巧】

先结论，后展开，最后落边界。

---

## 2.2 話し方の型

## 面接官

回答の型はありますか。

## 回答

あります。

```text
結論
 → 理由
 → ERIP での実装
 → 代替案との比較
 → 注意点
```

長く話す前に結論を置き、面接官が追問しやすい形にします。

## 追問

緊張して長い場合は。

## 回答

先に 20 秒結論を言い、詳細は『続けて説明できます』と区切ります。

## Point

- 結論先出し
- 追問余地を残す

---

## 2.3 案件切替

## 面接官

Java 案件なのに AI を長く話して良いですか。

## 回答

最初は良くありません。

案件に合わせて主プロジェクトを選び、共通自己紹介後に切替ます。
AI を話すのは面接官が関心を示してから、または AI 案件の時です。

## 追問

AI 案件では。

## 回答

ERIP を主に置き、Backend / RAG / Workflow / 権限監査を中心に話します。

## Point

- 案件適合を最優先

【学习提示】

Part01 の案件別オープニングとセットで使う。

# Chapter 3　TL 压迫问答

## 3.1 それは本当に完成か

## 面接官

それは本当に本番で使える完成形ですか。未完成を隠していませんか。

## 回答

完成した企業向けプラットフォームとして、
文書管理、RAG、分析、レポート、Approval、Audit、JWT/RBAC まで一連で実装しています。

検証用の stub モードやテスト用 InMemory はありますが、
それは品質確保の手段であり、正式業務経路の代替ではありません。
正式データは PostgreSQL、権限と監査がある状態で業務フローが通ります。

## 追問

では弱点は何ですか。

## 回答

外部モデル品質のばらつき、検索チューニングの継続、
運用面でのコスト最適化は継続課題です。
ただし中核業務フローとガバナンスは成立しています。

## Point

- 完成範囲を明確に
- 弱点は正直に、ただし核心は守る

【容易说错】

『其实还没做完』と自分から崩さない。范围を明確に语る。

## 3.2 なぜ Agent と呼ぶ

## 面接官

ただの API では。なぜ Agent と言うのですか。

## 回答

単一応答 API ではなく、目標に対して複数ステップを実行し、
ツール（検索・分析・生成）を使い、状態を持って業務を進めるためです。

ただし無制御の自律エージェントではなく、
権限・Workflow・Approval で制御された Agentic システムです。

## 追問

過剰な言い過ぎでは。

## 回答

『完全自律の万能 Agent』とは言いません。
業務上の Agent 的ワークフローを実装した、と正確に話します。

## Point

- 制御された Agentic Workflow
- 誇張しない

---

## 3.3 事故が起きたら

## 面接官

誤った経営レポートが出たら誰の責任ですか。システムは何をしますか。

## 回答

業務確定の責任分界は承認者にあります。

システムは、根拠 Citation、版管理、承認履歴、監査ログを提供し、
誰が何に基づき承認したかを追跡可能にします。
無審査確定を防ぐのが設計目的です。

## 追問

システムに責任は無いのですか。

## 回答

品質と制御を提供する責任はあります。
だから Retrieval 品質、権限、状態機械、監査を実装しています。
『AI が書いたから不可避』とは言いません。

## Point

- 人の責任分界 + システムの制御責任

---

## 3.4 コスト爆発

## 面接官

LLM コストが爆発したらどうしますか。

## 回答

用途別ルーティング、不要呼び出し削減、
キャッシュ可能な前処理、利用量 Ledger、予算/モード制御で抑えます。

すべてを最高品質モデルへ固定しないことが基本です。

## 追問

止められない呼び出しは。

## 回答

管理権限でモード制御や kill switch 的な運用手段を持ち、
異常時に安全側へ倒します。

## Point

- 用途分離
- 観測と制御

---

## 3.5 情報漏洩

## 面接官

社内文書が外部に漏れるリスクをどう抑えますか。

## 回答

JWT/RBAC、検索時 ACL、ログ秘匿、Secret 管理、
最小権限、監査で抑えます。

また、不要な全文を外部へ送らない、Prompt/ログに機密を出さない方針です。

## 追問

完璧に防げますか。

## 回答

リスクをゼロとは言いません。多層防御と検知、権限最小化で実用安全を作ります。

## Point

- 多層防御
- ゼロ断言しない

---

## 3.6 なぜあなたが必要か

## 面接官

ライブラリを繋げば誰でも作れるのでは。

## 回答

部品を繋ぐことと、企業業務として成立させることは別です。

権限、承認、監査、状態機械、失敗処理、運用、説明責任まで含めて
設計・実装できることが価値です。

ERIP はその全体を通した実装です。

## 追問

あなたの強みは。

## 回答

業務理解と Backend 設計、AI 部品の統制、日本語での設計説明です。
特定ライブラリ暗記だけではありません。

## Point

- 部品接続 ≠ 企業システム

# Chapter 4　技術比較

## 4.1 なぜ Spring Boot ではないか

## 面接官

なぜ Spring Boot で作らなかったのですか。

## 回答

Spring Boot は企業 Java で非常に強い選択です。

今回は AI/RAG/Python エコシステムとの統合速度、
Pydantic 契約、Workflow 実装を優先し FastAPI を選びました。
Java 案件では Spring を選びます。否定ではありません。

## 追問

Spring の経験は。

## 回答

Java/Spring 系の業務経験があります。
今回の AI プラットフォーム要件に FastAPI が適合した、という話です。

## Point

- 否定せず適合性
- 案件で選ぶ

【面试技巧】

永远先肯定 Spring 的企业价值。

---

## 4.2 Java と比較

## 面接官

Java と Python のどちらが企業向きですか。

## 回答

どちらも企業向きです。領域次第です。

大規模基幹、厳格な型と長期保守のチーム標準なら Java が強いことが多いです。
AI 周辺と高速な API 統合では Python が強いことが多いです。
ERIP は後者の中心課題が強かったため Python です。

## 追問

混在はあり得ますか。

## 回答

あり得ます。基幹は Java、AI サービスは Python、など境界を分けて連携します。

## Point

- 銀の弾丸なし
- 境界設計

---

## 4.3 なぜ Django ではないか

## 面接官

なぜ Django ではないのですか。

## 回答

Django は強力なフルスタック枠です。

ERIP は React を Frontend、API を Backend とし、
RAG/Workflow を明確なサービス境界で置く必要がありました。
API 中心 + AI 統合には FastAPI が適合しました。

## 追問

管理画面がある Django の利点は。

## 回答

管理機能を早く出す案件では利点大です。
今回の中心は企業 API と AI 業務流でした。

## Point

- 要件適合で選択

---

## 4.4 なぜ Node ではないか

## 面接官

なぜ Node.js ではないのですか。

## 回答

Node も API に強いです。

ただし今回の中心課題は RAG、Embedding、Python AI 周辺との統合でした。
チームとライブラリ資産を含めて Python/FastAPI を選択しました。

## 追問

Frontend が React なら Backend も Node では。

## 回答

同言語の利点はあります。ただし AI 実装効率とのトレードオフで Python を優先しました。

## Point

- 同言語利点 vs AI 効率

---

## 4.5 なぜ ChatGPT 単体ではないか

## 面接官

なぜ ChatGPT をそのまま使わないのですか。

## 回答

ChatGPT は優秀な汎用 AI です。

しかし社内文書の権限付き管理、根拠固定、承認、監査、業務フロー統合は
別途システムが必要です。

ERIP はそれらを含む企業プラットフォームです。

## 追問

ChatGPT を批判しますか。

## 回答

しません。用途が違います。汎用対話と企業業務基盤は役割が異なります。

## Point

- 汎用 AI vs 企業 Platform

【容易说错】

『ChatGPT は使えない』は失分。

---

## 4.6 なぜ RAG が必要か

## 面接官

なぜモデルを追加学習せず RAG ですか。

## 回答

社内文書は更新が頻繁で、権限や出典管理が必要だからです。

毎回学習し直すより、検索で最新根拠を渡す方が運用適合しやすいです。
必要に応じて学習手法は併用し得ますが、第一選択を RAG にしました。

## 追問

RAG の限界は。

## 回答

検索が弱いと回答も弱いです。だから Chunk、Hybrid、評価が重要です。

## Point

- 更新・権限・出典に強い
- 検索品質が前提

---

## 4.7 なぜ Approval / Audit か

## 面接官

AI が正しいなら Approval は不要では。

## 回答

AI は誤り得ます。経営資料は影響が大きいです。

生成と業務確定を分け、人の責任分界を残すために Approval が必要です。
Audit は後からの説明責任を支えます。

## 追問

開発速度が落ちませんか。

## 回答

落ちる部分はありますが、企業信用を買うコストです。
速度だけ最適化して事故る方が損失が大きいです。

## Point

- 責任分界
- 速度より信用

# Chapter 6　最終プレゼン

## 6.1 一分紹介

## 面接官

ERIP を 1 分で紹介してください。

## 回答

ERIP は大手流通グループ向け AI 経営分析プラットフォームです。

社内文書を登録し、RAG で根拠を取得し、AI が分析して取締役会向けレポートを生成します。
Approval と Audit までを一つの業務フローとして提供し、
私は FastAPI、React、PostgreSQL、JWT/RBAC、RAG、Workflow を中心に担当しました。

## Point

- 1分は業務価値中心

---

## 6.2 三分紹介

## 面接官

3 分で紹介してください。

## 回答

従来は資料が分散し、分析とレポート作成に時間が掛かり、根拠説明も困難でした。

ERIP では文書を一元管理し、Hybrid RAG で関連根拠を取得、
Workflow で分析とレポート生成を実行します。
生成結果は即確定せず Approval を経て、操作は Audit に残します。

Backend は FastAPI の Router/Service/Repository 構成、
認証は JWT、認可は RBAC、正式データは PostgreSQL です。
私は API、画面、データ、RAG、Workflow、承認監査の設計実装を担当しました。

## Point

- 課題 → 解決 → 設計 → 担当

---

## 6.3 五分紹介

## 面接官

5 分で紹介してください。

## 回答

ERIP、Enterprise Retail Intelligence Platform は、
経営企画を主利用者とする AI 経営分析プラットフォームです。

課題は三点、資料分散、レポート作成の長期化、根拠の残らなさです。
解決として、文書登録から Import/Chunk、Hybrid Retrieval、
分析 Workflow、レポート Version、Approval、Audit を統合しました。

技術的には React が操作し、FastAPI が API 境界、
Service が業務、Repository が PostgreSQL 永続化を担当します。
JWT で認証、RBAC で認可、LLM は Gateway 経由で統制します。
長時間処理は非同期化し、SSE で進捗を返します。

私の担当は API 設計、Frontend、データ設計、権限、
RAG、Workflow、Approval/Audit の実装です。
目的は AI を喋らせることではなく、説明可能な経営判断支援を企業運用に耐える形で提供することです。

## Point

- 5分で課題・主鎖・設計・担当・目的

## 回答

不合格に近いです。略語の後に必ず一言定義を付けます。

- 略語 + 一言定義
