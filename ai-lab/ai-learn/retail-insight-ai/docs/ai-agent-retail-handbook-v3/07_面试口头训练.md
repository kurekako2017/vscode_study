## 第二章 1 分钟回答训练

### 1. このシステムはどんな課題を解決しますか。

```text
小売の経営企画は会議前に POS・在庫・社内文書を集め、分析し、報告書を作り、
上長承認を取る必要があります。資料が散らばると根拠欠落と承認漏れが起きます。
ERIP は文書から RAG、明示 AI、取締役会報告、Approval、監査、Ledger までを一連化します。
```

### 2. システム全体の処理を説明してください。

```text
ユーザーがログインし JWT を受け取ります。文書を Upload し Import/Chunk します。
RAG で検索し Citation を得ます。必要なら明示 AI 分析（low_cost）を実行し、
取締役会報告（high_quality）を生成して ReportVersion を残します。
submit-approval 後、manager が approve/reject。すべて Persistent Audit と必要時 Ledger に残ります。
```

### 3. 一番工夫した設計は何ですか。

```text
費用と根拠の境界です。通常 RAG は既定ゼロ実 LLM。
明示 AI と取締役会報告だけ Gateway を通し、Evidence Gate、Idempotency、Decimal、Ledger を強制します。
```

### 4. JWT/RBAC を説明してください。

```text
Access Token は sessionStorage。role は admin/manager/employee。
権限は Registry から導出。未知 role は空権限。フロントは UX、Backend が権威。
401 はセッション破棄、403 は維持して拒否。
```

### 5. Approval 状態機を説明してください。

```text
generated → pending_approval → approved / rejected。
rejected 後は revise で新 ReportVersion、resubmit で再申請。
employee は submit、manager は review/approve。History は append-only。
```

### 6. LLM Gateway を説明してください。

```text
業務が SDK を直接呼ばないための唯一入口です。
ai_analysis は low_cost、executive_report は high_quality。
stub / openrouter / fallback_chain。Fallback は OR→NV→Gem→Local Qwen。
```

### 7. 障害時はどう調査しますか。

```text
request_id で Audit とログを横断し、業務状態、Ledger、Provider attempts、
DB 行、Frontend 表示の順で切り分けます。
```

### 8. 権限と監査をどう設計しますか。

```text
require_permission で能力境界、ownership で資源境界。
拒否も成功も Audit に残し、Key や全文は残しません。
```

### 9. PostgreSQL の役割は。

```text
正式 Repository。文書、Chunk、ReportVersion、Approval、Audit、Ledger、
AI Runtime を永続化します。Alembic head は 20260717_08_ai_runtime。
```

### 10. 配備を説明してください。

```text
ローカル完全開発は start_local.sh で 5173。Compose は compose_up.sh で 8080。
データソースは別。本番は HTTPS と独立 DB の別プロセス。Compose は単機受入可能でも
フル本番と同一とは言いません。
```

## 第三章 深掘り追问训练

### 1. 同期 API ですべて待てばよいのでは？

```text
KPI 長時間タスクや外部 Provider 待ちは HTTP timeout と UX 劣化を招きます。
文書/承認の多くは request/response ですが、Task 系は非同期 + 状態取得を使います。
```

### 2. 二重実行をどう防ぎますか。

```text
AI は Idempotency-Key、Approval は pending unique と行ロック、Upload は冪等キーです。
```

### 3. float でコスト計算してはだめですか。

```text
だめです。金額は Decimal。Ledger に policy snapshot を残し、後から設定変更しても履歴を改ざんしません。
```

### 4. なぜ ReportVersion が必要ですか。

```text
承認対象を不変化するため。改訂は新版を作り、旧版を上書きしません。
```

### 5. owner 以外が detail を読めるか。

```text
approval.review があればキュー/詳細可。employee は自分の submit 分を owner として読める設計です。
```

### 6. Kill Switch を入れたら。

```text
effective_mode が stub 強制。PostgreSQL に残るので再起動後も維持。
```

### 7. AI Runtime を InMemory で管理できるか。

```text
できません。503 fail-closed。企業設定は PostgreSQL 必須です。
```

### 8. Evidence が足りないとき。

```text
分析を拒否します。根拠なし課金と幻覚出力を防ぎます。
```

### 9. Fallback が全部失敗したら。

```text
失敗として Ledger/Audit に残し、成功レポートを作りません。
```

### 10. SSE が切れたら。

```text
Task 状態 API で再取得します。done と error を混同しません。
```

### 11. 401 を 403 と間違えると。

```text
401 でセッション破棄、403 で維持。取り違えると UX とセキュリティが壊れます。
```

### 12. フロントで role 文字列を直書きする問題。

```text
permission ヘルパに寄せます。Backend Registry が権威です。
```

### 13. seed を二回流すと。

```text
冪等。created=0 reused>0、provider_calls=0 を確認できます。
```

### 14. 5173 と 8080 のデータを混ぜると。

```text
別 DB です。混ぜて語ると受入が壊れます。
```

### 15. down -v したら。

```text
Compose volume が消え業務データ喪失。通常禁止です。
```

### 16. テスト数字を古い 281 で言ったら。

```text
誤りです。現在は PG 297/6 skip、InMemory 286/62 skip、FE 116。
```

### 17. Alembic head を 07 と言ったら。

```text
古いです。現 head は 20260717_08_ai_runtime。
```

### 18. 「JWT はまだ未完成」と言ったら。

```text
誤りです。JWT/RBAC は V1.0 実装済みです。
```

### 19. 「Approval に API がない」と言ったら。

```text
誤りです。submit/list/detail/approve/reject/revise/resubmit があります。
```

### 20. 「PostgreSQL はこれから」と言ったら。

```text
誤りです。正式 Repository は PostgreSQL。InMemory はテストのみ。
```

### 21. Redis の位置。

```text
将来キャッシュ/キュー候補。既定実行スタックではない。
```

### 22. VectorDB 専用製品は。

```text
現在は PostgreSQL/pgvector に統合。専用 VectorDB は拡張候補。
```

### 23. Lifecycle は SIEM か。

```text
違う。Frontend ローカル診断。Backend に送らない。
```

### 24. AI管理ページの権限。

```text
security.manage。通常は admin。
```

### 25. 文書ページから RAG へ。

```text
document_id クエリで /rag に handoff。
```

### 26. 報告から承認へ。

```text
submit 成功後 approval_id で /approval に handoff。pending 409 も提示。
```

### 27. ログに残さないもの。

```text
API Key、Secret、全文 Prompt、文書全文、パスワード、Authorization Header。
```

### 28. Docker は未検証と言ってよいか。

```text
いいえ。Compose スクリプトと health 受入がある。環境で daemon 停止時は別途説明する。
```

### 29. 本番と Compose の違いは。

```text
Compose は単機受入/デモ。本番は HTTPS、Secret 管理、独立 DB、監視など追加硬化が必要。
```

### 30. 一番弱い部分を正直に。

```text
有料 smoke 既定化、Billing UI、多テナント予算、SIEM/WORM、細粒度店舗 ACL。
```
